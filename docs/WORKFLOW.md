# 글 한 편의 작업 절차

> `WRITING.md`가 **무엇을 쓰는가**라면, 이 문서는 **어떤 순서로 쓰는가**입니다.
> AI에게 작업을 맡길 때 이 문서를 먼저 읽히세요.

---

## 0. 원칙

글의 목적은 발행이 아니라 **내가 그 주제를 체화하는 것**입니다.
그래서 절차가 "빨리 쓰기"가 아니라 **"이해한 뒤에 쓰기"** 로 설계돼 있습니다.

모르는 주제라면 3단계(학습)를 건너뛰지 마세요. 조사 자료만 가지고 쓴 글은
§1의 8번(출처 뭉뚱그림)이 반드시 티가 납니다.

---

## 1. 일곱 단계

```
① 주제 선정  →  ② 자료조사  →  ③ 학습(선택)  →  ④ 목차 합의
                                                      ↓
      ⑦ 발행   ←  ⑥ 검증 패스  ←  ⑤ 초안
```

각 단계는 **산출물이 나와야** 다음으로 갑니다. 산출물 없이 넘어가면 ⑥에서 되돌아옵니다.

| 단계 | 산출물 | 넘어가는 조건 |
|---|---|---|
| ① 주제 선정 | 한 줄 논지 | 날짜를 붙일 수 있는가 (`WRITING.md` §3) |
| ② 자료조사 | 조사 문서 1개 | 1차 출처만 남았는가 |
| ③ 학습 | 커리큘럼 + 단계별 정리 | 내 말로 설명할 수 있는가 |
| ④ 목차 | 섹션 제목 + 각 섹션 한 줄 | 4번·6번 항목이 있는가 |
| ⑤ 초안 | `src/content/posts/ko/*.md` (`draft: true`) | — |
| ⑥ 검증 | 수정된 초안 | 아래 체크 전부 통과 |
| ⑦ 발행 | 커밋 + push | 빌드 통과 |

---

## 2. ① 주제 선정

카테고리에서 고릅니다. 이전 글에서 고르지 않습니다(`WRITING.md` §3).

**논지를 한 줄로 못 쓰면 아직 주제가 아닙니다.** 다음 형태를 목표로 합니다.

```
X는 A까지를 정의한다. B는 정의하지 않는다. 그 경계가 C에게는 사소하지만 D에게는 전부다.
```

한 줄이 나오면 그게 글의 마지막 단락이 됩니다. 거기서 거꾸로 목차를 짭니다.

---

## 3. ② 자료조사

조사 결과는 **글이 아니라 별도 문서**로 먼저 만듭니다. 초안에 바로 녹이지 않습니다.
섞기 시작하면 어디까지가 확인된 사실인지 알 수 없게 됩니다.

**1차 출처만 남깁니다.**

| 쓴다 | 안 쓴다 |
|---|---|
| 표준 원문의 조항 번호 | "관련 표준에 따르면" |
| 논문 PDF · arXiv ID | 논문을 소개한 블로그 |
| 제조사 공식 문서 · 제품 브리프 | 기사 요약 |
| 저장소 코드 파일:줄번호 | README의 설명만 |
| 실제 로그 출력 | 기억 |

**숫자는 전부 출처를 붙여 적습니다.** 출처를 못 찾은 숫자는 조사 문서에서 지웁니다.
나중에 초안에 살아남아 발행됩니다. 실제로 2편에서 세 개가 그랬습니다.

---

## 4. ③ 학습 (모르는 주제일 때)

조사 문서를 읽었는데 **용어가 걸리면** 이 단계가 필요합니다. 건너뛰면 ⑥에서 드러납니다.

1. AI에게 **커리큘럼**을 짜게 합니다 (단계 / 소요시간 / 각 단계에서 읽을 것)
2. 0단계는 **내가 이미 아는 것과 잇는 단계**로 둡니다
3. 모르는 단어가 나오면 그 자리에서 물어봅니다. 넘기지 않습니다
4. 각 단계 끝에 **내가 요약**합니다. AI 요약을 읽는 것으로 대체하지 않습니다

> AI가 커리큘럼 난이도를 잘못 잡으면 바로 말하세요. 배경을 과대평가해서
> "이미 아는 것"으로 넘어간 부분이 나중에 글의 빈 곳이 됩니다.

코드 저장소가 있는 주제라면 **헤더부터** 읽습니다. `enum`, `struct`, 상수, 함수 이름만.
구현은 나중입니다. 이름이 설계 의도를 가장 정직하게 보여줍니다.

## 5. ④ 목차 합의

섹션 제목과 각 섹션 한 줄을 먼저 합의합니다. 바로 쓰기 시작하지 않습니다.

- `WRITING.md` §3의 4번(틀렸던 것)과 6번(모르는 것)이 목차에 **자리가 있는지** 확인
- 카테고리별 변형(§3)을 적용했는지 확인
- 섹션이 6개를 넘으면 글 두 편입니다

---

## 6. ⑤ 초안

두 가지 방식이 있고, 둘 다 씁니다.

**A. 내가 골격 → AI가 살** (`WRITING.md` §6의 권장)
훅·틀렸던 것·모르는 것·자동차↔로봇 대비를 내가 먼저 씁니다. 나머지를 AI가 채웁니다.

**B. AI가 전체 초안 → 내가 전면 수정**
주제가 크고 사실관계가 많을 때. 대신 **⑥ 검증을 훨씬 세게** 돌려야 합니다.
B로 갔으면 초안의 모든 문장을 의심하고 시작하세요.

### 피드백 표기

에디터에서 초안을 읽으면서 중괄호로 지시를 남깁니다. AI가 그걸 읽고 답하거나 고칩니다.

```
{이 문장 근거가 뭐야?}
{여기 너무 길어. 반으로}
{이 숫자 출처 확인해줘}
```

한 번에 다 읽고 한꺼번에 남기는 쪽이 왕복이 적습니다.

## 7. ⑥ 검증 패스

**순서대로** 돌립니다. 사실을 고치면 문체가 깨지고, 문체를 고치면 분량이 바뀝니다.

### 7-1. 사실

- [ ] 모든 숫자에 출처가 있는가 — 없으면 **지웁니다**, 완화하지 않습니다
- [ ] 논문 ID(arXiv 등)를 실제로 조회해 확인했는가
- [ ] 비율에 **분모**가 있는가 ("117번 발생"이 아니라 "60,000스텝 중 117번 = 0.2%")
- [ ] 정의를 원문 그대로 옮겼는가 — 비슷한 말로 바꾸면 틀립니다
      (예: "속도가 임계값 아래" ≠ "**변위**가 임계값 아래인 **연속** 스텝")
- [ ] 원문에 없는 수식어를 붙이지 않았는가 ("평균 저크" ≠ "Mean jerk **RMS**")
- [ ] 문서와 코드가 다르면 **둘 다** 적었는가

### 7-2. 문체

`WRITING.md` §1의 1~16번을 훑습니다. 특히 9~16번은 이 단계에서만 걸립니다.

### 7-3. 분량

`WRITING.md` §4 기준. 넘으면 **섹션을 통째로 빼는 쪽**이 문장을 줄이는 것보다 낫습니다.

### 7-4. 빌드

```bash
npm run build
```

한글 볼드 깨짐(`WRITING.md` §1 끝의 grep)을 이때 함께 확인합니다.

## 8. 다이어그램

색을 쓰지 않습니다. 본문 글자색을 그대로 물려받는 **단색 SVG**입니다.

| 요소 | 규칙 |
|---|---|
| 색 | `currentColor` 만. 채도 있는 색 금지 |
| 주 대상 | `stroke-width="1.6"`, 실선, 불투명 |
| 배경 요소 | `stroke-width="1"` + `opacity` 0.45~0.6 |
| 런타임 아님 | 점선 (`stroke-dasharray="5 5"`) |
| 글자 | 본문 13px / 보조 10.5px / 캡션 11.5px |
| 폭 | `width="100%"` + `style="max-width:720px;height:auto"` |
| 캡션 | 하단 점선 아래 1~2줄. 그림이 말하려는 한 문장 |

`<title>`과 `aria-label`을 반드시 넣습니다.
기존 예시: 3편 작업물(`halos_blockdiagram.svg`)의 구조를 그대로 따르면 됩니다.

## 9. ⑦ 발행

1. 프론트매터 `draft: true` → `false`
2. 태그 확인 (`WRITING.md` §8 — 형식 1개 + 주제 1~2개)
3. 커밋 — **AI가 커밋합니다**
4. push — **사람이 합니다** (아래 §10 참고)

### 커밋 메시지

```
<범위>: <소문자로 시작하는 명령형 한 문장>
```

범위는 `post` / `posts` / `draft` / `tags` / `docs` / `style` / `feat` / `fix`.
한 커밋에 한 가지 변경만.

```
post: publish the VLA failure-signature post
draft: cut section 4 and the remaining author claims
tags: split tags into form and subject, and write the rule down
```

## 10. 환경 제약 (AI 세션용)

이 저장소는 사용자 PC에 있고, AI는 브리지를 통해 접근합니다. 다음은 **안 됩니다.**

| 안 되는 것 | 대신 |
|---|---|
| 파일 삭제 (`rm`) | `_to_delete/` 로 이동 (`.gitignore`에 있음) |
| `git push` | AI가 커밋까지만. push는 사용자가 Windows에서 |
| Google Drive 파일을 컨테이너로 올리기 | 컨테이너에서 만들어 사용자에게 보낸 뒤 기록 |

추가로:

- `git` 작업 후 `.git/*.lock`, `tmp_obj_*` 가 남아 지워지지 않습니다.
  커밋 전후로 `_to_delete/gitjunk/` 에 쓸어 담고, 상태는 `git --no-optional-locks status` 로 봅니다.
- 빌드 확인은 소스를 tar로 묶어 클라우드 컨테이너에 올려 `npx astro build` 로 합니다.
  (`node_modules`, `dist`, `.git`, `_to_delete` 제외)
- 스크린샷은 컨테이너의 `/opt/pw-browsers/chromium` + playwright-core.

## 12. 게이트 — 자동화가 넘지 않는 선

절차의 일곱 단계 중 **사람이 반드시 들어가는 지점이 셋**입니다.
나머지는 자동으로 흘러도 되지만, 이 셋은 자동이 넘어가면 안 됩니다.

```
[자동]  주간 스캔 → 주제 후보 3~5개
             ↓
   ▣ 게이트 1   무엇을 쓸지 고릅니다                    몇 분
             ↓
[자동]  조사 → 학습 → 목차 제안
             ↓
   ▣ 게이트 2   목차 승인 + 경험 투입                   여기가 제일 큼
             ↓          훅 / 틀렸던 것 / 모르는 것 /
             ↓          자동차↔로봇 대비 — §6이 금지한 넷
[자동]  초안 → 검증 4패스 → 빌드 → 브랜치 push → PR
             ↓
   ▣ 게이트 3   프리뷰를 읽고 발행을 결정합니다            30분
             ↓
[자동]  머지 → 배포
```

### 게이트 3은 `draft: false` 입니다

**자동화가 `draft: false`로 바꾸지 않습니다.** 사람이 읽고 말한 뒤에만 바꿉니다.
초안 상태로 브랜치에 올라가는 것까지는 자동이고, 발행은 아닙니다.

PR을 쓰면 이 게이트가 저절로 생깁니다. 브랜치가 올라가면 배포 프리뷰가 뜨고,
읽고 머지하면 그게 발행입니다. 폰에서도 됩니다.

## 13. 병렬 — 몇 편까지

| 상태 | 상한 | 왜 |
|---|---|---|
| 집필 중 (게이트 2 통과) | **1편** | 게이트 2·3이 둘 다 집중을 요구합니다. 둘을 동시에 붙들면 문체가 흐려집니다 |
| 조사 중 (게이트 1~2) | **2편까지** | 세션이 혼자 합니다. 사람 시간 0. 다만 3편 넘으면 어느 게 어느 건지 헷갈립니다 |
| 학습 중 (트랙 B) | **1주제** | |

이 배치면 **주 2편**이 지속 가능합니다. 주 3편은 게이트 2를 주 3회 해야 해서 무리입니다.

### 세션마다 브랜치

병렬 세션이 같은 브랜치에 커밋하면 충돌합니다. 세션은 자기 브랜치에서만 일합니다.

```
post/03-halos-intro
post/04-halos-code
research/wam            ← 트랙 B. _research/ 만 건드림
docs/<무엇>             ← 절차·문체 문서 수정
```

`main`에 직접 커밋하지 않습니다. 머지가 곧 발행입니다.
